# Bop It Access の Git ワークフロー

Git は、プロジェクトのソース コードとドキュメントへの変更履歴を保存します。 **コミット**は、検査したり戻ったりできる名前付きスナップショットです。 GitHub はこのソース履歴を公開しているので、他の人がコードを読んで MOD を自分でビルドできるようになります。リポジトリには、コンパイルされた MOD ファイルまたは GitHub リリースは含まれません。

## これまでの歴史について

ビルドのソース アーカイブ `v0.1.0` を通して `v0.6.12` 37 の連続する Git コミットとしてインポートされました。各コミットは、対応するエントリを使用してソースの変更を記述します。 [BopItAccess-build-history.html](BopItAccess-build-history.html)。これらのコミットは Git インポート中に作成されたため、Git タイムスタンプは元のビルド日付ではありません**。彼らの主題はバージョン番号なしで変更を説明しています。ビルド履歴ドキュメントには、どのソース スナップショットが各バージョンに属しているかが記録されます。

リリース ZIP ファイル、コンパイル済み DLL、および一時ビルド出力は、Git のソース履歴の外に残ります。ビルド履歴ページは、対応する GitHub ソース コミットにリンクしています。既存のバージョン タグはローカルに残り、最初の GitHub パブリケーションの一部ではありません。 GitHub バージョン タグまたはリリースはまだ公開されていません。

Git コミットでは、Christopher Shaw の GitHub 応答不可アドレスを作成者として使用します。 Codex で書き込まれたコミットには、 `Co-authored-by` 作品に貢献したモデルの名前を示すトレーラー。セッション レコードでは、最初の履歴ビルドについては GPT-6 Luna、次の 36 については GPT-6 Sol が識別されます。モデルが後のコミットで変更される場合は、そのコミットのトレーラーでその新しい名前を使用します。

## 便利なコマンド

このプロジェクト ディレクトリで PowerShell を開き、次を実行します。

```powershell
git status                         # See changed, added, and untracked files
git diff                           # See changes that have not been staged
git log --oneline                   # Browse source commits
git show --stat HEAD~1             # See files changed in the preceding commit
```

これらのコマンドはリポジトリを検査するだけです。 MOD やインストールされているゲームは変更されません。

## 今後のビルドごとに

1. ソースを変更し、次のビルド バージョン番号を選択します。
2. いつものように MOD をビルドし、ローカル アーカイブを準備します。全体を含める `documentation` フォルダーに、英語ガイドとすべての翻訳言語のサブフォルダーが含まれ、すべてのインストール アーカイブに含まれます。ビルドをインストールするときに、そのフォルダーをゲームのインストールにコピーします。ゲーム内ガイドは、開くたびに現在のゲーム言語の HTML を読み取ります。ビルドを完了として記録する前に、結果を検査してください。コンパイルされたアーカイブは GitHub の外に残ります。
3. 走る `git status` そして `git diff`。どのファイルが変更されたかを確認してください。意図したソースとドキュメントの変更をステージングし、次の方法でレビューします。 `git diff --cached`.
4. 件名にバージョン番号を含まない説明的なソース コミットを作成します。を含める `Co-authored-by` Codex がコミットを書き込んだときの実際のモデル名を含むトレーラー。たとえば、 `git commit -m "feat(speech): add example setting" -m "Co-authored-by: MODEL NAME <noreply@openai.com>"`;交換する `MODEL NAME` そのコミットに使用されたモデルを使用します。
5. ビルドのエントリを追加します `BopItAccess-build-history.html`、既存のコミットスタイル形式を使用します。実際の変更、その理由、および関連する制限を説明し、ステップ 4 のソース コミットをリンクします。パッケージ化する前に、対応する翻訳済みコピーを更新します。同じ作成者と正確な共同作成者トレーラーを使用して更新履歴をコミットします。ローカルのドキュメント フォルダーを更新し、履歴ファイルが既にコピーされている場合はアーカイブします。
6. ソースコミットと履歴コミットの両方を公開します `git push origin main` 準備ができたら。これはブランチのみをプッシュします。ローカル バージョン タグをプッシュしたり、GitHub リリースを作成したりすることはありません。

ビルドを生成しない小さな作業には、独自のコミットを含めることができます。次のビルド コミットがそれに続くことができます。個人のログ、ゲームのインストール、生成されたバイナリ、その他のマシン固有のファイルをコミットから除外します。 GitHub リリースが後で役立つようになった場合は、その時点でタグとコンパイルされたダウンロードを決定します。

Git は新しい作業を自動的にアップロードしません。各ローカルコミット後、他の人が見る準備ができたら、意図的にプッシュします。
